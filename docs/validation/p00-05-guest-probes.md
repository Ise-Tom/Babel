## Exact sequence for one private cycle

1. Pass the runner's preflight, provision a unique run and retain its private journal. The runner now records redacted ISO build/edition/package/digest pins in that journal. Install the guest OS from the mounted, approved ISOs through the isolated VM console. The operator still has to configure Windows AD DS/DNS on `reference-dc` and start the matching Babel DNS/LDAP services on `babel-dc`; the scripts do not invent those services or a successful product probe.
2. Before running any guest script, supply a **private** staging manifest with exactly six role entries. Each entry names its single private NIC interface, a predeclared exact running build, nonempty expected package pins, and zero or more locally staged `.msu`/`.cab` (Windows) or `.deb` (Linux) updates. Every update needs its relative file path, SHA-256, HTTPS publisher terms, a private rights record and `approved_use = private_isolated_install_and_run`. An empty update list means the ISO and already installed packages must meet the predeclared build/package pins. Windows package pin values are KB identifiers; Linux values are exact `dpkg-query` versions. Keep this manifest and staged bytes outside Git.
3. Run [bundle preparation](../../scripts/reference_guest_evidence.py) with the provisioned journal, private staging manifest and a **new private output directory**. It verifies update rights and bytes before copying anything; then copies the exact [Windows](../../scripts/reference_guest_windows.ps1) or [Linux](../../scripts/reference_guest_linux.py) script, updates and per-guest `config.json`. The config binds run ID, canonical plan SHA-256, VM name, role, private IP/prefix, DNS zone/server, time source, expected build/packages, update hashes and script hash. Preparation writes the expectations to the journal only after all six bundles are ready. Transfer each bundle through the scoped isolated guest console or approved private media path; no download or public CI handoff is used.
4. Run the copied script **inside each installed guest** as administrator/root. The script immediately writes an incomplete `report.json`, then checkpoints each of nine steps: update hash verification, offline installation, one-NIC/static-IP check, isolated DNS, isolated time, exact running build/package observation, DC A/SRV and LDAP TCP discovery, time offset, and denied egress/default-route check. It writes `complete` only after all nine pass. An update requiring reboot, failed command, missing service or interrupted process leaves an incomplete record. Rerun after a required reboot and inspect the latest report; never edit it to claim success.
5. Copy six reports to a private host directory in `<guest-id>/report.json` layout. Run `discover` while VMs still exist to persist host-owned VM/switch observations in the journal. Then run `teardown` and verify its manifest-scoped cleanup. Finally run `assess`. It binds each report to the journal's run/plan, script and staged update digests and predeclared build/package pins; compares expected and observed IP, effective DNS, time offset, no default route, denied external TCP, DC A/SRV and LDAP TCP outcomes; and requires prior host discovery and all resources deleted. A structurally complete cycle record is **review evidence**, never P00-05 acceptance or proof that operator-supplied reports are independently authentic. Repeat on a fresh run ID for cycle two.

```powershell
python scripts/reference_guest_evidence.py prepare --journal D:\LabState\babel-lab-<run-id>.json --staging-manifest D:\LabMedia\guest-staging.json --output-root D:\LabBundles\<run-id>
# In each Windows guest, from its transferred bundle:
powershell.exe -NoProfile -File .\reference_guest_windows.ps1 -Config .\config.json -Report .\report.json
# In each Linux guest, from its transferred bundle:
python3 reference_guest_linux.py --config config.json --report report.json
# Back on the host, after all guest reports are copied privately:
python scripts/run_reference_lab.py discover --journal D:\LabState\babel-lab-<run-id>.json
python scripts/run_reference_lab.py teardown --journal D:\LabState\babel-lab-<run-id>.json
python scripts/reference_guest_evidence.py assess --journal D:\LabState\babel-lab-<run-id>.json --reports-root D:\LabReports\<run-id> --output D:\LabReports\<run-id>-cycle.json
```

The Linux script requires Python 3, `ip`, `systemd-resolved`, `chrony`, `dig` and `dpkg-query` from the preapproved offline image/packages. It writes a local chrony configuration with no external pool. `babel-dc` is its network's local time source; the reference Windows DC enables its Windows Time NTP service. Guest scripts require exactly one active private interface and refuse a default route. Time offsets are measured relative to the isolated DC, not an external UTC authority. Windows script uses DISM for updates and verifies KB presence through HotFix or installed package state. Neither script configures a forest, joins a domain, logs in a user, or qualifies product interoperability.
